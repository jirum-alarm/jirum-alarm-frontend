# 지름알림 디자인 시스템 놀이터

새 화면은 **이미 있는 조각을 골라 정해진 규칙대로 조립**한다. 숫자·색을 새로 고르지 않는다.
여기서는 그 조각과 규칙을 직접 만져 보고(오른쪽 아래 Controls), 툴바 「테마」로 다크도 본다.

## 다섯 층

값은 아래층에서 위층으로만 흐른다. 위층은 아래층의 **이름**만 쓴다.

- ① **토큰** — 색·글자 크기·모서리·그림자·차트 색. 원본 `packages/design-system/tokens.js` → 여기 「기초」
- ② **레시피** — 부품 모양(클래스 문자열). web·앱이 같은 값을 읽는다. 원본 `recipes.js` → 「레시피」
- ③ **부품** — 플랫폼별 컴포넌트(web DOM·앱 RN)와 언제 쓰나. 목록 `catalog.js` → 「소개/부품 지도」·「components」
- ④ **조립 규칙** — 화면 여백·섹션 간격·조작 높이·아이콘 크기. 원본 `layout.js` → 「조립 규칙」
- ⑤ **화면** — 부품을 규칙대로 놓은 것 → 「조립 규칙/조립 예시」

## 화면을 만들 때 순서

- ① **소개/부품 지도**에서 필요한 조각을 찾는다. 있으면 그대로 쓴다.
- ② 놓을 때 간격·높이는 **조립 규칙**의 이름(`layout.gutter`·`layout.stack.base`·`layout.control.touch`)으로.
- ③ 없으면 만들기 전에 web↔앱 짝을 먼저 찾는다. 새로 만들면 모양은 `recipes.js`, 목록은 `catalog.js`, 그리고 web 부품 옆에 스토리.
   등록을 빼먹으면 `catalog.test.mjs` 가 커밋을 막는다.

## 무엇이 자동으로 검증되나

- 모든 스토리가 **라이트·다크 두 번** 렌더되고, axe 접근성 검사(대비 AA·이름 없는 버튼·라벨 없는 입력칸)를 통과해야 한다.
- 조작 시나리오(play 함수)가 있는 스토리는 눌러 보고 결과를 확인한다(스위치가 켜지는지, 비활성 버튼이 안 눌리는지).
- 린트가 hex·기본 팔레트·임의 크기를 막고, 토큰 테스트가 theme.css·다크 키·대비를 본다.

로컬: `pnpm --filter design storybook`(만지기) · `pnpm --filter design test:stories`(검증).
